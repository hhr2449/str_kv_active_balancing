# 基础知识

## Attention 与 Transformer

语言模型的基本任务是：根据前面已经出现的 token，预测下一个 token。

例如，输入：

> 今天的天气很

模型需要根据前面的内容，判断下一个 token 更可能是什么，然后将生成的 token 加入序列，继续预测。

下面先以使用因果自注意力的 Transformer 语言模型为例，介绍一次预测中模型进行了哪些计算。

### Token Embedding 与隐藏状态

输入文本首先会被 Tokenizer 拆分成若干个 token，并转换为对应的 Token ID。

Token ID 是词表中的编号。模型会根据这个编号，从 Embedding 表中取出对应的向量，作为该 token 的初始表示。

可以写成：

```text
x_i = Embedding(token_id_i)
```

其中，`x_i` 是第 `i` 个 token 对应的向量。

如果输入共有 `n` 个 token，每个向量的维度为 `d_model`，那么把这些向量按顺序排列，就可以得到一个矩阵：

```text
X 的形状 = n × d_model
```

矩阵中的每一行对应一个 token。

这些向量进入 Transformer 层后，会不断经过计算和更新。某个 token 在网络中间某一层的表示，就称为它在这一层的**隐藏状态**。

也就是说：

- Token Embedding 是 token 刚进入模型时的表示；
- 隐藏状态是它经过模型处理后的表示；
- 每经过一层 Transformer，都会得到一组更新后的隐藏状态。

模型还需要利用 token 的位置信息，区分不同的排列顺序。

> [!tip]
>
> 位置信息的加入方式取决于模型。有的模型将位置向量加到 Embedding 上；RoPE 则会根据位置对 Attention 中的 Q、K 进行旋转变换。因此，不必把所有模型都理解为“Token Embedding 加上位置向量”。
>
> 相关原理见 [RoFormer](https://arxiv.org/abs/2104.09864)。

### Attention 的作用

一个 token 在句子中的含义，不只由它本身决定，还取决于它所在的上下文。

例如：

- 我吃了一个苹果。
- 我买了一部苹果手机。

处理“苹果”相关的 token 时，前面的内容会影响模型对它的理解。这里用词语说明含义，实际 Tokenizer 可能将一个词拆成多个 token。

因此，模型在处理某个 token 时，需要结合上下文中的其他 token 来更新它的表示。

Attention 机制的作用是：

> 为当前 token 可以关注的位置分配不同的权重，再根据这些权重，将相应位置的信息融合到当前 token 的表示中。

它通常不是只选择一个 token，而是对多个位置的信息进行加权组合。

这里讨论的是 **Self-Attention，即自注意力**：参与计算的 Q、K、V 来自同一条序列的隐藏状态。

### Attention 的计算过程

#### Query、Key 和 Value

为了计算 token 之间的匹配程度，模型会根据隐藏状态生成三种向量：

- Query，简称 `Q`；
- Key，简称 `K`；
- Value，简称 `V`。

可以写成：

```text
Q = X × W_Q
K = X × W_K
V = X × W_V
```

其中：

- `X` 是进入本次 Attention 投影计算的隐藏状态；
- `W_Q`、`W_K`、`W_V` 是模型通过训练得到的参数矩阵；
- 三个矩阵分别对同一组隐藏状态进行不同的线性变换。

为了突出主要过程，这里省略可能存在的偏置项。采用前置归一化的模型，会先对隐藏状态进行归一化，再计算 Q、K、V。

三种向量可以直观地理解为：

| 向量 | 作用                                |
| ---- | ----------------------------------- |
| Q    | 当前 token 想从上下文中寻找什么信息 |
| K    | 某个位置具有哪些可用于匹配的特征    |
| V    | 某个位置实际能够提供的信息          |

也就是说，模型先通过 Q 和 K 确定如何分配权重，再根据这些权重读取 V 中的信息。

#### 计算 token 之间的匹配分数

对于第 `i` 个 token，可以用它的 Query 与第 `j` 个 token 的 Key 做点积：

```text
score(i, j) = q_i · k_j
```

这个分数表示：第 `i` 个位置在本次 Attention 计算中，对第 `j` 个位置的匹配程度。

固定当前 Query 后，匹配分数越高的位置，在后续 softmax 中会获得越高的权重。

将所有位置的 Query 和 Key 组成矩阵，就可以统一计算：

```text
Scores = Q × K^T
```

其中，`K^T` 表示矩阵 `K` 的转置。

假设共有 `n` 个 token，Q、K 的向量维度都是 `d_k`：

```text
Q 的形状      = n × d_k
K^T 的形状    = d_k × n
Scores 的形状 = n × n
```

分数矩阵中：

- 第 `i` 行表示第 `i` 个 token 对各个位置的匹配分数；
- 第 `i` 行、第 `j` 列表示 `q_i` 与 `k_j` 的匹配分数。

#### 缩放与因果掩码

得到点积分数后，先除以 Q、K 向量维度的平方根：

```text
ScaledScores = Scores / sqrt(d_k)
```

这样做是为了控制点积的数值尺度，避免维度较大时分数差异过大，使 softmax 的结果过于集中。

接下来，还需要加入**因果掩码，Causal Mask**。

在自回归语言模型中，第 `i` 个位置只能关注自己以及前面的位置，不能关注后面的位置。

例如，一条序列包含 4 个 token：

| 当前处理的位置 | token 1 | token 2 | token 3 | token 4 |
| -------------- | ------- | ------- | ------- | ------- |
| token 1        | 可关注  | 屏蔽    | 屏蔽    | 屏蔽    |
| token 2        | 可关注  | 可关注  | 屏蔽    | 屏蔽    |
| token 3        | 可关注  | 可关注  | 可关注  | 屏蔽    |
| token 4        | 可关注  | 可关注  | 可关注  | 可关注  |

原因是：第 `i` 个位置的隐藏状态会用于预测第 `i+1` 个 token。如果计算时提前读取后面的内容，就相当于看到了要预测的答案。

可以定义一个掩码矩阵 `M`：

```text
M(i, j) = 0       当 j ≤ i
M(i, j) = -∞      当 j > i
```

将掩码加到缩放后的分数上：

```text
MaskedScores = Q × K^T / sqrt(d_k) + M
```

这样，未来位置的分数会变成负无穷，在 softmax 中对应的权重为 0。

> [!tip]
>
> 因果掩码限制的是“每个位置可以使用哪些信息”，不要求模型一定逐个位置计算。对于已经给定的一整段输入，多个位置的计算仍然可以并行进行，只要屏蔽不允许访问的未来位置。

#### Softmax 与注意力权重

随后，对加上掩码的分数执行 softmax：

```text
AttentionWeights = softmax(MaskedScores)
```

这里的 softmax 是**逐行进行的**。

例如，第 `i` 行对应当前 token 对上下文各个位置的分数，就在这一行内部归一化，得到它对各个位置的注意力权重。

处理后：

- 每个权重都大于或等于 0；
- 每一行的权重之和等于 1；
- 被因果掩码屏蔽的位置，权重为 0。

假设某个位置可以关注三个 token，最终得到的权重为：

```text
AttentionWeights = [0.6, 0.3, 0.1]
```

这表示本次计算会更多地使用第一个位置的信息，其次是第二个位置，最后是第三个位置。

#### 对 Value 加权求和

得到注意力权重后，当前 token 按照这些权重，对可关注位置的 Value 进行加权求和：

```text
Output_i = Σ AttentionWeight(i, j) × v_j
```

对于因果自注意力，上面的 `j` 只需要遍历 `1` 到 `i`，也就是当前及之前的位置。

沿用前面的权重示例：

```text
Output_i = 0.6 × v_1 + 0.3 × v_2 + 0.1 × v_3
```

得到的结果仍然是一个向量，但它已经融合了多个位置提供的信息。

如果对所有位置一起计算，就可以写成矩阵形式：

```text
Output = AttentionWeights × V
```

假设每个 Value 的维度为 `d_v`：

```text
AttentionWeights 的形状 = n × n
V 的形状                = n × d_v
Output 的形状           = n × d_v
```

也就是说，每个 token 都得到了一个融合上下文信息后的输出向量。

#### Attention 的整体公式

将前面的步骤合起来，因果自注意力可以写成：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}+M\right)V
$$

整个过程是：

1. 根据隐藏状态生成 Q、K、V。
2. 使用 Q 与 K 的点积计算匹配分数。
3. 对分数进行缩放，并屏蔽未来位置。
4. 逐行执行 softmax，得到注意力权重。
5. 根据权重对 V 加权求和，得到各个位置的输出。

> [!tip]
>
> Attention 中的 softmax 得到的是“对上下文各个位置分配多少权重”。后面 LM Head 的 softmax 得到的是“词表中哪个 token 更可能成为下一个 token”。这两次 softmax 的作用不同。

### 多头注意力

前面的过程描述了一个注意力头。

token之间的关联式多维度的，比如：词性、位置、语义、语法等

一个注意力头很难兼顾多个维度，所以使用多个注意力头，每个注意力头主要提取一个方面的关联

各个头分别生成 Q、K、V，并计算各自的注意力输出。

对于第 `r` 个头：

```text
Q_r = X × W_Q_r
K_r = X × W_K_r
V_r = X × W_V_r

head_r = Attention(Q_r, K_r, V_r)
```

然后把各个头的输出拼接起来，再经过输出映射：

```text
MultiHead(X) = Concat(head_1, head_2, ..., head_h) × W_O
```

其中，`h` 是头的数量，`W_O` 将拼接后的结果映射回模型的隐藏维度。

这样，同一个 token 可以通过不同的头，从不同的表示空间中提取上下文信息。每个头的具体作用由训练形成，不是预先规定好的。

这里先使用标准多头注意力说明原理。部分模型会让多个 Query 头共享 K/V 头，后续讨论 KV Cache 空间时再介绍。

### Transformer 层中的其他计算

Attention 是 Transformer 层的一部分。一个常见的 Transformer 层还包含残差连接、归一化和前馈网络。

#### 残差连接

Attention 的结果通常会加回这一层输入的隐藏状态：

```text
X_next = X + AttentionResult
```

也就是说，在原有表示的基础上，加入本次 Attention 得到的信息。残差连接也有助于深层网络的训练。

#### 归一化

归一化会调整隐藏向量的数值尺度，帮助模型保持稳定的计算和训练过程。

常见形式包括 LayerNorm 和 RMSNorm。这里先了解它们的作用，不展开具体公式。

不同模型的归一化位置有所不同。下面使用前置归一化，即 Pre-Norm，说明整层结构。

#### 前馈网络 FFN

Attention 之后，隐藏状态还会进入前馈网络，简称 FFN。

FFN 对每个位置的隐藏向量分别进行非线性变换。在同一层中，不同位置通常使用同一套 FFN 参数。

用一个基础形式表示：

```text
FFN(x) = Activation(x × W_1 + b_1) × W_2 + b_2
```

其中，`Activation` 是非线性激活函数。部分模型会采用带门控的结构，具体形式有所不同。

可以这样理解两者的分工：

- Attention 根据其他位置的信息更新当前表示；
- FFN 对当前表示中的特征继续进行变换。

#### 一层 Transformer 的整体过程

一个采用 Pre-Norm 的 Transformer 层，可以简化为：

```text
Y = X + MultiHead(Norm_1(X))

X_out = Y + FFN(Norm_2(Y))
```

具体过程是：

1. 将输入隐藏状态 `X` 归一化，送入多头注意力。
2. 将注意力输出加回 `X`，得到 `Y`。
3. 将 `Y` 归一化，送入 FFN。
4. 将 FFN 输出加回 `Y`，得到本层输出 `X_out`。

两次残差连接分别保留了对应子层的输入信息。

### 多层 Transformer 与下一 Token 预测

模型会堆叠多层 Transformer。上一层的输出，作为下一层的输入。

每一层根据自己的参数，重新计算这一层的 Q、K、V，并更新隐藏状态。因此，同一个 token 在不同层中的 K、V 也不同。

经过最后一层以及模型所需的最终归一化后，每个位置都会得到最终隐藏状态。



在普通自回归生成中，如果当前输入共有 `n` 个 token，我们使用**最后一个位置的最终隐藏状态**，预测第 `n+1` 个 token。

可以写成：

$$
\text{logits}=h_{\text{last}}W_{\text{vocab}}+b
$$

其中：

- `h_last` 是最后一个位置的最终隐藏状态；
- `W_vocab` 将隐藏状态映射到词表大小；
- `logits` 包含词表中每个 token 的预测分数；
- `b` 是可选的偏置项，有些模型不使用。

随后，通过 softmax 得到下一 token 的概率分布：

```text
P(next token) = softmax(logits)
```

模型再按照生成策略选择一个 token，例如选择概率最高的 token，或者根据概率进行采样。

预测了一个新的token之后，需要将预测的token加入当前的序列，进一步计算当前token的隐藏状态，以此预测下一个token，循环往复，得到最终结果：

- 使用当前最新token的Q和之前的token的K、V进行注意力计算
- 得到当前最新token的最终隐藏状态，还需要将当前token的K、V加入Cache中
- 使用这个最终隐藏状态预测下一个token
- 将新的token加入序列，重复以上过程

> [!tip]
>
> 可以发现一个token的隐藏状态的计算之和它前面的token有关，所以前面的token的K，V无需重新计算，可以直接复用，只需用当前token的Q和前面token的 KV Cache 进行注意力计算即可得到当前token的隐藏状态，然后再将当前token的KV加入Cache中，循环往复即可





- Prefill：从输入token到计算出最终隐藏状态
- Decode：利用已有的KV Cache，通过自回归反复预测下一个token

KV Cache的作用主要体现在两处：

1. Prefill计算的时候要先去查看当前的输入token是否命中KV Cache，如果命中，可以直接取用，节省了Prefill阶段的计算量
2. Prefill阶段计算结果会被添加到KV Cache中，Decode阶段会在已有的KV Cache的基础上计算当前token的隐藏状态，然后将当前token的KV追加到KV Cache中

可以发现两个阶段的重点是不同的：

- Prefill阶段主要在计算。一层层地计算token的K，V，Q和隐藏状态，所以是计算密集型
- Decode阶段主要在访存。在前面token的KV Cache的基础上计算当前token的隐藏状态，然后追加当前token的KV Cache。这个过程的计算量很少，但是需要大量访存

于是现在的推理引擎往往会将这两个阶段分离，有Prefill Pod和Decode Pod，这样能更好地利用两个阶段的特性，比如Mooncake

## 模型推理过程

### 准备阶段

#### 服务启动与模型加载

在接收用户请求之前，推理服务通常需要先完成初始化：

1. 读取模型配置，例如层数、隐藏维度和注意力头数。
2. 加载已经训练好的模型权重，将其放到负责计算的 GPU 上。
3. 加载 Tokenizer，以及模型使用的对话模板等配置。
4. 准备运行时需要的显存、缓存空间和调度组件。

初始化完成后，服务就可以持续接收请求。

#### 整理输入与 Tokenization

对于聊天模型，用户看到的当前问题，往往只是模型输入的一部分。

一次请求的输入可能还包括：

- 系统提示词，例如助手的身份和回答要求。
- 之前的对话历史。
- 当前用户输入。
- 检索到的资料、工具说明或工具返回结果。

系统会按照模型对应的 **Chat Template，对话模板**，将这些内容组织成模型能够识别的格式。

例如，模板可以通过特殊标记区分哪些内容来自用户、哪些内容来自助手，以及接下来应该由谁回答。具体标记取决于模型。

整理后的输入再经过 Tokenizer，转换为一串 Token ID：

```text
input_ids = [x₁, x₂, ..., xₙ]
```

其中，`n` 表示输入 token 的数量。实际实现也可以由同一个接口完成模板应用和分词。

Token ID 是词表中的编号。进入模型之后，还需要通过 Embedding 层，将这些编号转换为向量。

> [!tip]
>
> 多轮对话中，模型能够利用之前的交流内容，通常是因为相关历史被包含在当前输入中。服务还可以复用历史前缀的 KV Cache，以减少重复计算。

### 开始推理

输入准备好之后，请求会进入推理引擎，例如 SGLang 或 vLLM。

推理引擎负责组织模型的执行，包括：

- 将等待执行的请求放入队列。
- 根据计算资源和缓存空间，选择当前执行哪些请求。
- 将适合一起计算的请求组成 Batch。
- 维护请求的生成状态，并逐步返回结果。

> **Batch，批次**，可以理解为一起交给模型计算的一组工作。
>
> 例如，多个请求都处于生成阶段时，引擎可以在同一批计算中，为每条请求分别推进一个 token。每条请求仍然使用自己的上下文。
>
> 因此，请求到达服务的时刻，与它真正开始在 GPU 上执行的时刻，可能存在间隔。这个间隔中的一部分就是排队等待时间。

#### Prefill 阶段

Prefill 可以理解为：

> 处理输入上下文，为后续生成准备状态，并得到预测第一个新 token 所需的输出。

假设当前输入包含 `n` 个 token：

```text
input_ids = [x₁, x₂, ..., xₙ]
```

这些 token 会经过 Embedding 和多层 Transformer。对于每一层，模型会计算相应的 Q、K、V，并按照因果掩码进行 Attention。

在这个过程中：

- 每个输入位置都可以使用它自身及之前位置的信息。
- 各层产生的 K、V 被保留下来，形成这条请求的 KV Cache。
- 最后一个输入位置的最终隐藏状态，用于预测第一个新 token。

##### 如果存在可复用的前缀缓存

当输入前缀已经有可用的 KV Cache 时，系统可以复用这些状态，减少前缀部分的重复计算。

例如，当前输入有 1,000 个 token，其中前 800 个 token 的 KV 可以直接复用，那么剩余 200 个 token 仍然需要处理。

处理后面的 token 时，Attention 会继续使用前面 800 个 token 的 KV。也就是说，复用前缀省去了已有状态的重建，但这些历史状态仍然参与后续计算。

#### 从模型输出中选择第一个 token

Prefill 得到最后一个输入位置的最终隐藏状态后，LM Head 会将它映射为词表中各 token 的分数，也就是 logits。

根据这些分数，可以得到下一个 token 的概率分布，再按照生成规则选出 `y₁`。

常见的选择方式包括：

| 方式             | 含义                                                     |
| ---------------- | -------------------------------------------------------- |
| Greedy，贪心选择 | 每一步选择当前概率最高的 token                           |
| Sampling，采样   | 按照概率分布随机选择 token，也可以结合温度等设置调整分布 |

选出 `y₁` 后，系统就得到了第一个生成 token。如果还需要继续生成，就进入 Decode 阶段。

#### Decode 阶段

Decode 可以理解为：

> 使用已经生成的内容和缓存的上下文状态，继续逐步预测后面的 token。

此时，输入部分的 KV 已经由 Prefill 准备好，第一个新 token `y₁` 也已经选出。

接下来，模型会将 `y₁` 作为新的输入，完成以下计算：

1. 将 `y₁` 的 Token ID 转换为 Embedding。
2. 在每一层中，为 `y₁` 计算当前层的 Q、K、V。
3. 使用当前 Q，对历史缓存及当前 token 的 K、V 进行 Attention。
4. 保留 `y₁` 在各层产生的 K、V，扩展已有缓存。
5. 得到 `y₁` 的最终隐藏状态，经过 LM Head，预测 `y₂`。

以此类推，不断重复这个预测过程

#### Prefill 与 Decode 的对照

| 对比项               | Prefill                                  | Decode                         |
| -------------------- | ---------------------------------------- | ------------------------------ |
| 主要处理对象         | 输入上下文中需要计算的部分               | 上一步新生成的 token           |
| token 内容是否已知   | 输入内容已经确定，可组织多个位置一起计算 | 后续内容需要依次预测           |
| KV Cache 的变化      | 建立或补齐输入部分的 KV                  | 每一步增加当前输入 token 的 KV |
| 得到的生成结果       | 第一个新 token                           | 后续的新 token                 |
| 与用户体验的主要联系 | 影响多久开始收到回答                     | 影响开始回答之后的生成速度     |
| 阶段特点             | 计算密集型                               | 访存密集型                     |

### 停止生成与返回文本

自回归生成会一直继续，直到满足停止条件。

常见的停止条件包括：

- 生成了配置的结束 token，例如 EOS 或对话轮次结束标记。
- 生成内容匹配了指定的停止字符串。
- 达到了最大生成长度，例如 `max_new_tokens` 指定的上限。
- 用户取消请求，或服务终止了这次请求。

模型产生的结果仍然是一串 Token ID，需要通过 Tokenizer 转换为文本，用户才能看到回答。

请求结束后，引擎会清理该请求的运行状态，并释放它占用的资源。启用前缀缓存时，部分 KV 可以继续保留，供后续请求复用；具体保留和淘汰规则由缓存管理机制决定。

### 推理过程中常见的时间指标

结合上面的过程，可以区分几个常见指标：

| 指标                      | 含义                                  | 主要观察的问题     |
| ------------------------- | ------------------------------------- | ------------------ |
| TTFT，Time to First Token | 从发出请求到收到首个生成 token 的时间 | 多久开始回答       |
| ITL，Inter-Token Latency  | 相邻生成 token 之间的时间间隔         | 回答过程中是否流畅 |
| 端到端时延                | 从发出请求到完整回答结束的时间        | 整个请求多久完成   |

这里使用用户侧的观测口径。实际工具可能在服务内部记录时间，或者按流式消息记录到达间隔，比较数据时需要统一起止点和统计方式。

TTFT 除了受 Prefill 计算影响，还会受到输入处理、排队、必要的缓存读取或传输，以及结果返回等环节的影响。

ITL 除了受单步模型计算影响，还会受到请求调度和通信等因素的影响。一次回答中，各步的时间间隔也可能不同。



## KV Cache

KV Cache 的作用是：**保存已经处理过的 token 在各层产生的 K、V，供后续计算复用，减少重复计算。**

### 为什么可以缓存 K、V

回忆 Attention 的计算，当前 token 需要使用：

- 自己的 Query。
- 历史 token 和自身的 Key、Value。

在因果自注意力中，一个位置只能看到它自身及之前的内容。因此，向序列末尾追加新 token 时，前面位置的上下文保持不变，已经计算出的 K、V 可以继续使用。

例如，输入从 `[A, B, C]` 扩展为 `[A, B, C, D]` 后，A、B、C 对应的 KV 可以复用，只需继续计算 D，并让 D 使用已有的历史 KV。

历史 Query 通常不需要长期保存，因为处理 D 时使用的是 D 自己的 Query。

### 推理过程中的 KV Cache

**1. Prefill 阶段**

如果没有可复用缓存，模型会处理输入 token，并保存它们在各层产生的 K、V。最后一个输入位置的输出用于预测第一个新 token。

如果输入前缀已经有可用 KV，则可以复用这部分状态，只继续处理剩余输入。例如，1,000 个输入 token 中，前 800 个命中缓存，就可以省去这 800 个位置的重复计算。

处理后面 200 个位置时，仍然需要读取前面的 KV，获得历史上下文信息。

**2. Decode 阶段**

> Prefill 阶段产生的 KV Cache 会传给 Decode 阶段使用,Decode计算出新的token的Q,K,V之后会将其追加到KV Cache中

每一步 Decode 都会：

1. 将上一步生成的 token 送入模型，计算它的 Q、K、V。
2. 使用当前 Q，对历史和当前位置的 K、V 进行 Attention。
3. 保存当前 token 的新 KV，并预测下一个 token。

例如：

| 阶段          | 本次处理的内容 | 新增的 KV     | 预测结果 |
| ------------- | -------------- | ------------- | -------- |
| Prefill       | 输入 `A、B、C` | A、B、C 的 KV | D        |
| 第一步 Decode | D              | D 的 KV       | E        |
| 第二步 Decode | E              | E 的 KV       | F        |



## KV Cache 的管理

前面介绍了 KV Cache 中保存什么。接下来以 SGLang 的常规 Radix Cache 为例，看看系统如何查找、使用和释放这些缓存。

### 缓存如何组织

可以将缓存管理理解为三个部分：

| 部分                      | 作用                                              |
| ------------------------- | ------------------------------------------------- |
| 前缀索引 `RadixCache`     | 记录已经缓存的 token 前缀，以及对应的 KV 存储位置 |
| 请求映射 `ReqToTokenPool` | 记录当前请求的各个 token 使用哪些 KV 存储位置     |
| KV 存储池与分配器         | 保存实际的 K、V 数据，管理可分配和可回收的空间    |

前缀索引用于查找可复用内容；请求映射让模型找到本次计算需要的 KV；存储池负责保存数据。

#### 压缩前缀树

SGLang 使用 **Radix Tree，压缩前缀树**，组织共享前缀。

- 树节点：保存一段 Token 序列及其 KV 存储索引。
- 节点之间的路径：表示这些 Token 序列的前后拼接关系。

比如:

```
请求 A：[a, b, c, d, e, f]
请求 B：[a, b, c, d, x, y]
```

这两个请求执行完成后,会被组织成:

<img src="https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261102230115709.png" alt="image-20261102230115709" style="zoom:33%;" />

节点的key就是该节点表示的token序列，value是对应的存储槽位索引

从根节点到某个节点的路径对应一个完整的前缀

**查找：** 从根节点出发，根据当前请求的 Token 序列依次匹配各节点的 `key`，寻找最长的已缓存前缀。如果在某个节点内部匹配结束，则将该节点拆分，使匹配到的前缀成为独立节点。最终返回匹配长度及对应的 KV Cache 存储索引。

**插入：** 将新的 Token 序列插入前缀树，保留已有的公共前缀，并为新增部分建立分支。如果新旧序列在某个节点内部发生分歧，则先拆分节点，再添加新的分支。

例如:

```
1. 请求 A 执行完成，插入缓存
请求 A：[a, b, c, d, e, f]

Root
  |
[a, b, c, d, e, f]


2. 请求 B 到达，查找最长公共前缀
请求 B：[a, b, c, d, x, y]
已有缓存：[a, b, c, d, e, f]

命中：[a, b, c, d]


匹配在节点内部结束，将节点拆分：
Root
  |
[a, b, c, d]
  |
[e, f]


3. 请求 B 复用前缀，计算剩余部分并插入缓存
       Root
         |
   [a, b, c, d]
      /       \
  [e, f]    [x, y]


4. 请求 C 到达，查找并插入
请求 C：[a, b, c, d, x, z]
命中：[a, b, c, d, x]
新增：[z]


最终前缀树：
          Root
            |
      [a, b, c, d]
        /       \
    [e, f]      [x]
                / \
              [y] [z]
```

> [!tip]
>
> 注意只有前缀完全相同的部分才能够进行复用（因为Prefill计算是要依赖前面的上下文的）

### 一次请求的缓存管理流程

**1. 查找缓存**

请求到达后，`RadixCache` 根据输入 Token 序列查找最长的已缓存前缀，返回命中的 KV Cache 存储索引。

**2. 复用与分配**

系统将命中的 KV 索引写入 `ReqToTokenPool`，并对这些缓存加锁，避免运行期间被淘汰。对于未命中的 Token，则从 KV 存储池中分配新空间。

如果空间不足，就通过 **LRU 策略**，从未被引用的叶节点开始淘汰缓存，释放对应的 KV 存储空间。

**3. 执行推理**

- **Prefill：** 复用命中的前缀 KV，只计算未命中的输入部分。
- **Decode：** 随着生成过程推进，为新处理的 Token 分配空间并写入 KV，同时更新请求映射。

**4. 请求结束**

系统将新计算且适合保留的 KV 登记到 `RadixCache`，解除缓存的引用保护，并释放请求映射。

保留的 KV 仍占用存储池空间，可以供后续请求复用，直到未来空间不足时被淘汰。

## 推理引擎与集群架构

当大量用户同时发送请求时，系统如何通过多个 GPU、多个推理实例共同提供服务，以及 KV Cache 如何在不同实例之间复用和传输。

### 1. 推理引擎内部架构

以 SGLang 为例，一个推理引擎可以简化为以下几个模块：

<img src="https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261102232352143.png" alt="image-20261102232352143" style="zoom:33%;" />

Scheduler总调度模块

Worker执行具体的计算

其中 Scheduler 是整个推理引擎的核心控制模块，它需要根据请求状态和可用资源，持续决定 GPU 下一步执行什么。

### 2. 批处理

> 将多个请求组织成一个 Batch，在一次模型计算中同时执行这些请求
>
> 为了提高GPU的利用率，如果一次模型执行只处理一个请求，利用率低
>
> 注意这些请求是并行执行的，他们有自己的上下文、KV Cache等，只是同一批进行计算

假设 GPU 上同时有三个请求：

```
请求 A：正在生成第 10 个 Token
请求 B：正在生成第 20 个 Token
请求 C：正在生成第  5 个 Token
```

如果依次执行：

```
GPU：处理 A → 处理 B → 处理 C
```

每次只推进一个请求，容易造成 GPU 利用率不足。

因此，推理引擎会将多个请求组织成一个 Batch（批次），在一次模型执行中同时推进这些请求：

```
Batch = [A, B, C]

GPU 一次前向计算：
  A → 生成下一个 Token
  B → 生成下一个 Token
  C → 生成下一个 Token
```

每个请求仍然拥有自己的上下文、KV Cache 和生成状态，只是共同参与一批 GPU 计算。

### 3. Worker、GPU、Pod 与多副本部署

| 概念            | 含义                                                         |
| --------------- | ------------------------------------------------------------ |
| GPU             | 实际执行模型计算和存储 KV Cache 的硬件                       |
| Worker          | 推理系统中执行计算或承担特定任务的工作进程、执行单元         |
| Pod             | Kubernetes 中的部署单位，可以包含一个或多个容器，并使用一个或多个 GPU，可以理解为一个计算实例 |
| Replica（副本） | 一份能够独立提供服务的模型推理实例                           |
| Node（节点）    | 通常指一台物理服务器或虚拟机，可以拥有多个 GPU、运行多个 Pod |

这些概念并非严格一一对应。

例如，一台服务器拥有 8 张 GPU，可以有不同的部署方案。

#### 方案 A：每张 GPU 运行一个模型副本

```
服务器（8 GPUs）
│
├── Pod 1 → 模型副本 1 → GPU 0
├── Pod 2 → 模型副本 2 → GPU 1
├── Pod 3 → 模型副本 3 → GPU 2
│
└── ...
    Pod 8 → 模型副本 8 → GPU 7
```

每个副本拥有自己的模型权重、调度状态和 KV Cache，可以独立处理请求。

这种方式体现了 数据并行（Data Parallelism，DP） 的基本思想：不同模型副本处理不同请求。

> DP：数据并行，运行多个模型副本，副本之间独立运行，分别处理请求

#### 方案 B：多个 GPU 共同运行一个模型副本

```
服务器（8 GPUs）
│
├── Pod 1：模型副本 1
│    ├── GPU 0
│    ├── GPU 1
│    ├── GPU 2
│    └── GPU 3
│
└── Pod 2：模型副本 2
     ├── GPU 4
     ├── GPU 5
     ├── GPU 6
     └── GPU 7
```

假设每个模型副本使用 4 张 GPU，通过 Tensor Parallelism（TP，张量并行） 将模型计算和参数分布在多个 GPU 上。

这种情况下：

- 一个模型副本对应多个 GPU。
- 多个 GPU 需要相互通信，共同完成一次模型前向计算。
- 一个副本内部的 KV Cache 也可能按照注意力头等维度分布在不同 GPU 上。

另外还有 Pipeline Parallelism（PP）等模型并行方式，可以将不同模型层放在不同设备上。

DP 与 TP 的主要区别：

- DP：不同副本分别处理不同请求，扩大整体服务能力。
- TP：多个 GPU 共同执行一个模型副本，支持更大模型或更高的单实例计算能力。

在实际集群中，通常会组合使用 DP、TP、PP，而一个逻辑推理副本也可以跨越多个服务器或 Pod，因此不能简单认为一个 Pod 必然等于一个模型副本。

> TP：张量并行，使用多个卡来运行一个模型，一层内的矩阵切分到多卡上进行计算，然后在 all_reduce 拼回来。通信成本较高，当一张卡装不下一个模型的时候可以张量并行
>
> PP：将模型的不同层放到多张卡上计算，需要点对点通信

### 4. 请求路由：多个副本如何共同服务

当系统部署多个模型副本时，需要一个 Router（请求路由器），决定每条请求交给哪个副本处理。

例如：

```
                 用户请求
                    |
                  Router
                 /  |  \
                /   |   \
             Pod A Pod B Pod C
              GPU   GPU   GPU
```

这里的 Router 与单个推理引擎内部的 Scheduler 负责不同层面的决策：

- Router： 决定请求应该交给哪个推理实例。
- Scheduler： 决定该实例内部哪些请求组成 Batch，以及何时执行。

#### 常见的路由策略

| 策略         | 选择方式                             |
| ------------ | ------------------------------------ |
| Random       | 随机选择一个副本                     |
| Round Robin  | 轮流选择副本                         |
| Least Loaded | 选择负载较低的副本                   |
| Cache-Aware  | 优先选择已经保存相关 KV Cache 的副本 |
| 混合策略     | 同时考虑缓存亲和性与负载             |

其中，Cache-Aware Routing 与之前介绍的 KV Cache 复用直接相关。

假设：

```
Pod A 缓存：[a, b, c, d, e]
Pod B 缓存：[a, b]
Pod C 缓存：[]

新请求：[a, b, c, d, x]
```

如果将请求分配给 Pod A，可以复用 4 个 Token 的 KV；分配给 Pod B 只能复用 2 个；分配给 Pod C 则需要重新计算全部输入。

因此，优先选择 Pod A 可以减少 Prefill 计算。

但如果 Pod A 已经很繁忙，而 Pod B 几乎空闲，那么将请求分配给 Pod B 也可能获得更低的整体响应时延。

所以路由需要平衡两个目标：

1. Cache Locality（缓存亲和性）：尽量使用已有缓存。
2. Load Balancing（负载均衡）：避免大量请求集中到少数副本。

> [!tip]
>
> 这里就是我们的研究主要针对的地方，通过主动KV干预平衡各个pod之间的负载，在提升缓存利用效率的同时能够改善负载均衡，减少排队



### 5. PD 分离：Prefill 与 Decode 分别执行

之前介绍过，Prefill 与 Decode 的计算特点不同：

|              | Prefill        | Decode                 |
| ------------ | -------------- | ---------------------- |
| 主要工作     | 处理输入 Token | 逐步生成 Token         |
| 资源特点     | 计算密集型     | 访存密集型             |
| 主要性能目标 | 降低 TTFT      | 降低 ITL，提高生成吞吐 |

#### 为什么要进行 PD 分离？

在传统部署方式中，同一个推理引擎既负责 Prefill，又负责 Decode。

```
Pod A：
  Prefill + Decode

Pod B：
  Prefill + Decode
```

假设某个 GPU 正在为多个请求执行 Decode，此时一个很长的 Prompt 到达，需要大量 Prefill 计算。

即使引擎采用连续批处理，这种长时间或大量的 Prefill 工作也可能影响已有请求的生成速度。

因此，可以将两种工作分配给不同的推理实例，称为 Prefill-Decode Disaggregation（PD 分离）。

<img src="https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261102233845613.png" alt="image-20261102233845613" style="zoom:33%;" />

### 6. KV Cache 的跨节点传输

假设 Prefill 在 Pod P1 完成，而 Decode 要在 Pod D1 执行。

```
Pod P1                         Pod D1
┌────────────────┐             ┌────────────────┐
│ GPU 0          │             │ GPU 1          │
│                │             │                │
│ Prefill        │   KV Cache  │ Decode         │
│ KV Cache       │ ──────────> │ KV Cache       │
│                │   RDMA      │                │
└────────────────┘             └────────────────┘
```

一次典型的传输过程：

1. Prefill Pod 处理输入，计算出对应的 KV Cache。
2. Decode Pod 准备接收缓存的存储空间。
3. 两侧协调源地址、目标地址、传输长度等信息。
4. 通过网络将 KV 数据传输到 Decode Pod。
5. 传输完成后，Decode Pod 使用这些 KV 继续生成。

需要区分两个部分：

- 控制面（Control Plane）：决定传输什么、从哪里传、传到哪里，以及传输何时完成。
- 数据面（Data Plane）：实际搬运 K、V 张量。

#### Mooncake 的作用

Mooncake 提供的主要能力包括：

| 组件             | 作用                                       |
| ---------------- | ------------------------------------------ |
| Transfer Engine  | 在 GPU、CPU 内存和不同节点之间高效传输数据 |
| Mooncake Store   | 提供分布式缓存存储能力和缓存对象管理       |
| 元数据与控制服务 | 管理缓存对象位置、副本和传输相关元数据     |

其中，Transfer Engine 支持 RDMA 等高速传输方式，可以降低大规模 KV 数据搬运的开销。

注意，PD 分离只需要支持 P/D 之间的 KV 传输，不一定需要部署共享 KV Store。共享存储池是进一步实现跨实例缓存复用的一种方式。

### 7. 主动 KV Cache 干预的位置

前面介绍的缓存管理和请求路由，主要根据当前请求以及缓存状态进行决策。

但是，在多 Pod 集群中，还可以主动改变 KV Cache 的分布，例如提前复制可能被使用的缓存。

假设：

```
Pod A：缓存前缀 X
Pod B：没有前缀 X
```

系统发现前缀 X 可能很快会在 Pod B 被使用。

此时可以采取不同策略：

策略一：请求路由

将未来使用 X 的请求直接分配给 Pod A。

优点是可以直接利用已有缓存，不需要跨节点复制；缺点是 Pod A 可能出现负载集中。

策略二：被动 KV 传输

请求到达 Pod B 后，发现需要前缀 X，再从 Pod A 传输相应的 KV。

这种方式能够减少重复计算，但请求可能需要等待数据传输。

策略三：主动 KV 复制

在请求到来之前，系统预测前缀 X 未来可能在 Pod B 被使用，于是提前复制：

```
初始状态：

Pod A：[X]
Pod B：[]

       主动复制 X
Pod A ────────────> Pod B

复制完成：

Pod A：[X]
Pod B：[X]
```

如果之后的请求确实被分配给 Pod B，它就可以直接使用已经存在的 KV Cache。

不过主动复制存在额外成本：

- 消耗网络带宽。
- 占用目标 Pod 的 KV Cache 容量。
- 复制的数据可能始终没有被使用。
- 新复制的缓存可能挤占其他更有价值的缓存。

因此，主动干预需要综合考虑缓存复用收益、负载均衡、网络传输开销以及缓存容量。

#### 主动干预可以发生在哪些位置？

| 位置             | 可以采取的策略                         |
| ---------------- | -------------------------------------- |
| Router           | Cache-Aware 路由、负载感知路由         |
| Scheduler        | 根据缓存命中、资源使用情况调整请求调度 |
| KV Cache Manager | 调整缓存保留、淘汰和准入策略           |
| 分布式 KV 管理层 | 在 Pod 之间复制、迁移、预取或删除缓存  |
| Transfer Engine  | 执行实际的跨节点 KV 数据搬运           |

其中，主动复制与迁移通常需要上层策略决定何时传输、传输哪些缓存、目标是哪一个 Pod，再由传输组件执行数据移动。

## HiCache

HiCache 是 SGlang 的分成 KV Cache 管理机制。它的核心作用是利用 GPU 显存、CPU 内存以及可选的外部存储，共同保存和复用历史 KV Cache。

> 分层存储：GPU、CPU 和可选的外部存储共同保存历史 KV。
>
> 分层命中：Device Hit 可以直接复用；Host Hit 需要先加载到 GPU；Miss 需要重新计算或从其他来源恢复。
>
> 写入与淘汰：Write-through / Write-back 决定缓存何时备份；淘汰机制决定什么时候释放某一层的空间。
>
> 缓存驻留位置：同一个前缀可能同时存在于 Device 和 Host，也可能只保留在其中一层。

### 分层的必要性

推理是在 GPU 上进行的，从 GPU 的显存读写数据肯定是最高效的。但是显存容量优先放不下全部的KV Cache，所以需要将host中的内存和外加的存储也加入进行，构成多层存储体系

<img src="https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261103105224385.png" alt="image-20261103105224385" style="zoom:33%;" />

L1 是GPU显存，速度快，容量小，可以直接用于推理

L2是CPU的内存，容量较大，使用前必须先搬回GPU才能使用

### 存储组织

之前已经介绍过了sglang使用RadixCache来组织KV Cache

每个树节点保存：

- `key`：一段 Token 序列。
- `value`：对应 KV Cache 的存储位置索引。
- `children`：后续前缀分支。

HiCache 在这个思路上进一步使用 HiRadixTree。

区别是：原来的 RadixCache 主要记录 GPU 上的 KV 位置；HiRadixTree 还会记录缓存在 Device、Host 等不同存储层中的驻留情况。

例如：

```
                    Root
                      |
                  [a, b]        Device + Host
                      |
                  [c, d]        Host
                   /   \
                [e,f] [x,y]
```

a,b在device和host中都有副本，而c,d只在host中有

现在请求 B 到来：

```
请求 B：[a, b, c, d, z]
```

HiCache 查询前缀树：

1. `[a,b]` 在 Device，直接复用。
2. `[c,d]` 在 Host，需要先加载到 Device。
3. `[z]` 没有缓存，需要重新 Prefill。

可以得到：

| Token   | 缓存情况   | 系统动作          |
| ------- | ---------- | ----------------- |
| `[a,b]` | Device Hit | 直接复用          |
| `[c,d]` | Host Hit   | 从 CPU 加载到 GPU |
| `[z]`   | Cache Miss | 执行 Prefill      |

Host Hit 也属于缓存复用，它可以避免重复 Prefill，但需要额外的数据传输时间。

### 写策略

#### 1. Write-through：及时备份

假设请求 A 刚刚计算完成：

```
Device：[A]
Host：  []
```

如果使用 `write_through`，系统会及时向 Host 写入 A 的备份：

```
Device：[A]
Host：  [A]
```

此时两层中都有 A。

之后，如果 GPU 空间不足，Device 中可淘汰的 A 被回收：

```
Device：[]
Host：  [A]
```

#### 2. Write-back：需要淘汰时再写回

假设使用 `write_back`：

```
Device：[A]
Host：  []
```

A 暂时只留在 GPU 中。

当 GPU 空间不足，需要回收 A 时，先将其写入 Host，再释放 GPU 中的缓存。

```
Device：[]
Host：  [A]
```

区别在于向 Host 写入的时机。

| 策略                      | 何时写入 Host              | 特点                               |
| ------------------------- | -------------------------- | ---------------------------------- |
| `write_through`           | 缓存被使用或产生后及时备份 | 保留更多备份，但写入开销较多       |
| `write_back`              | 上层缓存需要淘汰时写回     | 减少提前写入，但淘汰时可能需要等待 |
| `write_through_selective` | 达到访问热度等条件后写入   | 选择性保存热点缓存                 |

这些是 HiCache 官方支持的写入策略。



## 混合 mamba 架构

### 核心思想

在 full-KV 的经典架构中，需要保存每一层的 K，V，所以随着上下文的增长，KV Cache也会不断地增长

而 Mamba、线性注意力一类机制采用另一种方式：将历史信息不断更新到一个固定大小的递归状态中。

假设这个状态叫 S，可以简化表示为：

$S_t=F(S_{t-1},x_t) $

其中：

- $S_{t-1}$：前面所有 Token 处理后的状态。
- $x_t$：当前 Token 的输入表示。
- $S_t$：处理当前 Token 后的新状态。

例如：

```
初始状态 S0
    |
处理 A → S1
    |
处理 B → S2
    |
处理 C → S3
    |
处理 D → S4
```

之后处理 E，只需要使用 $S_4$ 和 E，便可以更新状态。

这样将一个token的历史K，V压缩成了一个状态S，这样就避免了不断增长的K，V

但固定大小的状态也意味着历史信息经过了压缩，模型无法像 Full Attention 一样直接对所有历史位置分别计算注意力权重。

因此，混合架构将两种机制结合：大部分层使用高效的递归计算，少部分层保留 Full Attention

### Qwen3.5-4B 的混合架构

<img src="https://raw.githubusercontent.com/hhr2449/pictureBed/main/img/image-20261103111030024.png" alt="image-20261103111030024" style="zoom:33%;" />

每一组使用三个线性注意力层和1个full-attention层，然后重复8次，总共32层

因此，模型运行时需要同时保存两类历史信息：

| 层类型               | 保存的状态         | 特点                                          |
| -------------------- | ------------------ | --------------------------------------------- |
| 8 层 Full Attention  | Full-KV            | 每个 Token 有对应的 K、V，随着上下文增长      |
| 24 层 Gated DeltaNet | 递归状态、卷积状态 | 随 Token 处理不断更新，大小不随上下文线性增长 |

### 混合架构中的 KV Cache 管理

在混合架构中，出了要保存 K，V，还需要保存线性注意力层的状态

sglang中采用State Checkpoint的方式进行保存

也就是在原本的Radixtree中的部分节点保存节点对应的状态

此时，最长公共 Token 前缀，不一定等于实际能够完整复用的前缀长度。能够复用的是与当前请求匹配的最长公共前缀所对应的、最近的有效 Mamba State 检查点。



## P2Ptransfer

### 1. 基本工作流程

```
                 Gateway
                    |
         查询缓存位置、判断负载
                    |
          ┌─────────┴─────────┐
          |                   |
       Source Pod          Target Pod
       （缓存较全）        （负载较低）
          |                   |
          └──── KV Transfer ──>
                              |
                         复用前缀缓存
                              |
                         执行剩余 Prefill
```

Gateway 根据 KV Events 维护的缓存索引选择 Source，再根据负载条件选择 Target。

实际数据由 Mooncake 传输，Target 接收到数据并完成校验后，才会将其正式加入本地缓存。

### 2. 两种传输模式

| 模式             | 数据来源                      | 当前支持情况                                              |
| ---------------- | ----------------------------- | --------------------------------------------------------- |
| `DEVICE`         | Source GPU 中的 KV Cache      | 支持 Full-KV 及必要的 Mamba State，但要求完整前缀驻留 GPU |
| `HICACHE_DIRECT` | Source CPU Host 中的 KV Cache | 可直接传输 Host 缓冲区，但当前不支持 Mamba State          |

要特别注意，DEVICE模式可以传输full-KV和mamba state，但是要求传输的东西在device上

host则不支持mamba state，这也就是我们主动干预失败的关键点

### 3. 传输需要满足一定条件

P2P 并非只要两个 Pod 存在相同模型就能直接复制。

主要限制包括：

- 前缀匹配：通过 Token ID 和 Block Hash 确定待传输的公共前缀，并满足页对齐要求。
- 缓存驻留：Source 必须实际保存完整、可传输的前缀状态。
- 模型兼容：Source 和 Target 需要有兼容的模型、缓存布局和并行配置。
- 目标容量：Target 必须有足够空间保存传来的缓存。

其中，Gateway 的 KV Events 可能存在延迟，所以 Gateway 认为某个前缀存在，不代表 Source 当前一定还能传输它。



### 4. 当前实现是请求驱动的

它通常在以下情况触发：

1. 请求到达，Gateway 找到拥有最长缓存前缀的 Source。
2. Source 的负载明显高于其他节点。
3. Gateway 选择负载较低的 Target。
4. 将请求需要的前缀缓存复制过去，再让 Target 处理请求。

主动 KV 干预则希望在请求到来之前，预测热点前缀并提前复制。

这是两者最关键的区别。

### 5. 传输有成本，也可能失败

一次传输会占用网络带宽、Source/Target 资源及目标缓存容量。

传输失败时，系统通常回退到本地重新 Prefill，保证普通请求能够继续执行；如果发生无法保证缓存一致性的严重错误，则有更严格的处理机制。

因此，P2P 策略必须考虑：

$\text{收益} = \text{避免的 Prefill 计算} - \text{传输与资源成本} $

而主动复制还要考虑未来有没有请求真正使用这份缓存。
