# 主动KV干预：项目概况

## 1. 背景

### 1.1 回顾项目目标

#### 问题

缓存亲和策略导致负载不均衡

```
                Gateway
                   |
       ┌───────────┼───────────┐
       |           |           |
     Pod A       Pod B       Pod C
       |           |           |
    有前缀 X     没有 X      没有 X
    负载很高     负载较低     负载较低
```

按照缓存亲和策略(AFF)，由于pod A具有前缀A，Gateway为了尽可能地增加KV Cache的命中，会将很多的请求分配到pod A

结果就形成了正反馈：

```
Pod A 拥有更多热点缓存
          ↓
Gateway 更倾向于选择 A
          ↓
A 接收更多同类请求
          ↓
A 保留更多相关缓存
          ↓
继续吸引请求
```

缓存多的pod能够吸引更多的请求，更多的请求又使其积累了更多的相关缓存，导致正反馈，形成了负载不均衡现象

如果按照负载均衡路由策略，将请求发给最闲的pod，这样可以优化负载均衡，但是请求被发到缓存少的pod，又会造成Prefill阶段命中少的问题

这就形成了两难：

- **亲和路由**：把请求发给「已经缓存了它前缀」的 pod → 命中高，但同类请求全堆到同一个 pod，正反馈越滚越偏（实测负载不均 ≈ 随机分配的 **3.73 倍**）；
- **均衡路由**：发给最闲的 pod → 均衡，但命中低，prefill 全量重算。

两难：命中高 = 负载失衡，负载均衡 = 命中低。

#### 我们的解决思路：主动干预

主动将缓存复制到其他的pod，这样多个pod都持有了缓存，即使采用AFF策略，也不会导致负载不均

```
                  Gateway
                     |
       ┌─────────────┼─────────────┐
       |             |             |
     Pod A         Pod B         Pod C
       |             |             |
     KV(X) ──────> KV(X)         KV(X)
       |             |             ^
       └───────────────────────────┘

       三个 Pod 都拥有前缀 X
```

尝试了三种主动干预策略：

| 机制      | 工作方式                                  |
| --------- | ----------------------------------------- |
| Proactive | 根据历史热度预测热点前缀，提前复制        |
| Broadcast | 将共享模板前缀广播到多个 Pod              |
| Recall    | 请求发生缓存未命中时，从其他 Pod 召回前缀 |

| 特征         | Proactive                  | Broadcast                | Recall                 |
| ------------ | -------------------------- | ------------------------ | ---------------------- |
| 触发时机     | 未来请求到达前             | 未来请求到达前           | 请求发生 Miss 时       |
| 复制对象     | 预测的热点前缀             | 公共模板前缀             | 当前请求缺失的前缀     |
| 是否需要预测 | 需要热度判断               | 需要识别稳定模板         | 不需要预测需求         |
| 目标 Pod     | 选择需要提前部署缓存的 Pod | 多个 Pod，通常尽可能覆盖 | 当前需要缓存的 Pod     |
| 主要风险     | 预测错误、无效复制         | 副本占用容量较大         | 增加当前请求的等待时间 |

- proactive：根据热度预测热点，将预测的热点提前复制
- Broadcast：识别常用的公共模板，将其广播到所有pod
- Recall：当缺失的时候在调取缓存到发生缺失的pod

> [!tip]
>
> 这些主动干预策略都需要使用P2PTransfer进行传输，我们之前一直在关注主动干预是否有收益，什么样的干预策略更优，但是却没有关注主动干预必要的传输是否能够正确进行

### 1.2 目前的状况

整体目标仍然是通过主动干预改善缓存亲和带来的负载不均衡问题

之前的模拟器建立在每个pod只有单层cache的基础上，并且认为传输都能够成功

2. 把这些实际约束加入模拟器

## 2. 真实系统实验发现的问题

### 2.1 实验现象

 fork B / Pro5000 上的一组真实实验：

- 6 个 Prefill Worker、1 个 Decode Worker。

- 模型架构：

  Hybrid SSM（混合状态空间模型），将状态空间模型（mamba架构）与传统的注意力机制混合

  qwen3.5-4b，32 层 = 24 层 linear_attention ＋ 8 层 full_attention

- 启用了 HiCache 分层缓存，`hicache-ratio=2.0`，即 **Host Cache 的配置容量约为 Device Cache 的 2 倍**。实验中某个 Prefill Worker 的缓存使用情况如下：

  | 指标           | 实测使用量                       |
  | -------------- | -------------------------------- |
  | Device Full-KV | 29,170 Token（约一个请求的规模） |
  | Host Cache     | 905,372 Token                    |

  同时启用了 `--hicache-write-policy write_through`（写直达策略），新产生的 KV Cache 会及时备份到 Host，Device 中不再使用的历史缓存则可以在容量压力下被回收。

  因此，实验中观察到 **Device 主要保留当前或近期请求的 Full-KV，而大量历史 Full-KV 保存在 Host**。混合模型还需要保存对应的 Mamba State。需要注意，`write_through` 本身不会立即清除 Device 中的缓存，具体淘汰由缓存管理机制决定；上述数字是实际使用量，并非缓存容量上限。

- 548 条真实 Agent 请求。



实验中一共发起 1,508 次主动传输：

| 传输类型  | 成功 | 拒绝  | 成功率 |
| --------- | ---- | ----- | ------ |
| Broadcast | 0    | 615   | 0%     |
| Proactive | 14   | 879   | 1.57%  |
| 合计      | 14   | 1,494 | 0.93%  |

成功的 14 次都是 128 或 256 Token 的浅前缀，448 Token 及以上的深前缀没有成功案例。

开启主动干预的实验和不开启的对照组的前缀命中率几乎相同

失败信息：

```
source residency probe failed

source cache does not cover
the requested transferable prefix

device=0 host=0
```

说明传输失败并不是传输链路本身有问题，而是在开启传输之前就因为source没有找到要求的可传输前缀而拒绝了

### 2.2 失败原因分析

#### 原因一：Gateway 索引滞后

在实际系统中，Gateway 负责主动 KV 干预的决策与调度。各 Worker 在新增或删除 KV Cache 时，会产生对应的 KV Events（如 `BlockStored`、`BlockRemoved`）。这些事件不会立即发送给 Gateway，而是先进入 Worker 本地的事件队列，再按照一定周期批量发布。

Gateway 根据收到的 KV Events 维护全局前缀缓存索引，记录各 Pod 持有哪些前缀，并据此选择 Source 和 Target，发起主动 P2P Transfer。

收到传输请求后，P2P Transfer 不会直接相信 Gateway 的缓存记录，而是先对 Source 进行 **Residency Probe**，重新检查待传输前缀的实际缓存状态：

- **完整 GPU 命中**：选择 `DEVICE` 模式。
- **完整 Host 命中且不需要 Mamba State**：选择 `HICACHE_DIRECT` 模式。
- **前缀不足或不满足传输条件**：拒绝传输，回退到本地重算。

问题在于，**Gateway 维护的缓存索引与 Worker 的实际缓存状态之间可能存在时间差**。例如，某个 Worker 已经淘汰了前缀 X，并产生了 `BlockRemoved` 事件，但事件仍停留在本地队列中，尚未发送给 Gateway。此时 Gateway 仍认为该 Worker 持有 X，因此可能继续选择它作为 Source，发起主动复制请求。最终 Source 在 Residency Probe 时无法找到对应前缀，返回 `source cache does not cover`，导致传输失败。

相比之下，正常的 **Prefill → Decode 被动 KV 传输**针对的是当前请求刚完成 Prefill 的 KV。Prefill Worker 直接通过请求的 KV 索引获取对应的物理缓存位置，传输期间相关资源受到请求生命周期管理，不需要通过 Gateway 的历史缓存索引重新查找。因此，它不会遇到上述由 KV Events 滞后引起的 Source 缓存失效问题。

**总结：** Gateway 的 KV Events 采用异步批量发布机制，可能使全局缓存索引滞后于 Worker 的实际缓存状态。主动干预依赖该索引选择历史缓存的 Source，因此可能向已经淘汰对应前缀的 Worker 发起复制请求，最终在 Source Residency Probe 阶段失败。

#### 原因二：Mamba 架构与 P2P Transfer 路径的矛盾

真实实验使用的是 Qwen3.5-4B 混合模型，包含 **24 层 Linear Attention（Gated DeltaNet）和 8 层 Full Attention**。因此，复用历史前缀时，不仅需要 Full Attention 层的 KV Cache，还需要对应的 Mamba State（递归状态），才能正确恢复模型的计算状态。

实验启用了 HiCache 分层缓存，`hicache-ratio=2.0`，即 Host Cache 的配置容量约为 Device Cache 的两倍，同时启用了 `--hicache-write-policy write_through`（写直达策略）。新产生的 KV Cache 会及时备份到 Host，而 Device 中不再使用的历史缓存可以随着容量压力被回收。

实验中某个 Prefill Worker 的缓存使用情况如下：

| 指标           | 实测使用量                       |
| -------------- | -------------------------------- |
| Device Full-KV | 29,170 Token（约一个请求的规模） |
| Host Cache     | 905,372 Token                    |

可以看到，实验中 **Device 主要保留当前或近期请求的 Full-KV，而大量历史 Full-KV 保存在 Host**。因此，主动干预希望复制的历史热点前缀，通常已经不再完整驻留于 GPU。

目前 P2P Transfer 提供两条传输路径：

- `**DEVICE**` **模式**：从 Source 的 GPU 直接传输 Full-KV，并支持传输所需的 Mamba State。但要求待传输的完整前缀仍然驻留于 Device。由于历史缓存大多已从 GPU 中被回收，因此通常无法满足这一条件。
- `**HICACHE_DIRECT**` **模式**：直接从 Source 的 Host Cache 向 Target 传输缓存，不需要先加载回 GPU。但当前实现不支持 Mamba State，要求 `requires_mamba=False`。对于使用混合架构的 Qwen3.5-4B，`requires_mamba=True`，因此这条路径无法使用。

这样就产生了一个矛盾：**主动干预主要需要复制历史热点前缀，而这些前缀的 Full-KV 大多保存在 Host；**`**DEVICE**` **模式要求完整的 GPU 缓存，**`**HICACHE_DIRECT**` **模式又不支持混合模型所需的 Mamba State。** 即使 Source 仍然保存着对应的历史缓存，也可能无法通过现有 P2P Transfer 接口完成复制。

**总结：** 当前混合 Mamba 模型的缓存管理方式与 P2P Transfer 的传输能力不匹配。历史 Full-KV 主要驻留 Host，而现有 Host 传输路径不支持 Mamba State，导致主动干预缺少可用的完整传输路径。这是当前实现中的机制性限制，无法仅通过调整热点预测、复制时机或路由策略解决。

## 3. 当前的任务

### 目标一：建立主动 KV 干预的离线收益模型

目前真实集群的实验结果表明，主动 KV 干预虽然具有潜在收益，但由于缓存驻留状态和 P2P Transfer 的限制，大部分主动复制无法成功执行。因此，我们需要利用真实实验日志，建立离线收益模型，**量化主动干预的潜在收益、实际可行性及执行成本，判断在什么条件下主动干预能够产生正收益。**

这部分主要使用 `offline_modeling_dataset_full.tar.gz` 中的真实实验数据，包括请求元数据、缓存命中记录、路由决策和传输日志。

具体分为三个部分：

1. **分析真实实验结果**：统计 Broadcast、Proactive 等策略的传输成功率、失败原因和传输长度，并比较实际缓存命中率与理想命中率。当前实验的目标命中率为 86.16%，实际命中率为 54.92%，两者相差 31.24 个百分点，需要分析这部分潜在复用空间为什么没有转化为主动干预收益。
2. **建立传输可行性模型**：结合传输日志和实际系统的存储架构，分析一次主动复制能否成功执行。重点考虑 Source 是否仍然持有对应前缀、Full-KV 的 Device/Host 驻留位置，以及当前传输路径是否支持所需的 Mamba State。
3. **建立收益与损失模型**：在传输可行性约束下，估计主动复制节省的 Prefill 计算成本，并综合考虑 KV 传输开销、无效复制和缓存占用带来的淘汰损失，计算主动干预的净收益。

此外，还需要考虑两种假设性的系统改进：**支持从 Host 传输 Mamba State，以及将热点前缀保留在 Device**，分析解决传输限制后，主动干预能够获得多少额外收益，又需要付出多少成本。

**总结：** 通过真实日志建立传输可行性与收益/损失模型，解释主动干预在当前系统中为什么难以获得收益，并进一步量化改善传输条件后可能获得的收益。



整个研究可以分为三个阶段。

#### 1. 建立传输可行性模型

利用真实的 `transfer.jsonl` 数据，将每次主动复制尝试作为一个样本，预测它是否能够成功。

输入包括请求的前缀长度、干预类型、Source/Target、缓存驻留状态等。

输出：

$P(\text{Transfer Success}\mid X) $

这个模型不是追求分类精度，而是用于验证核心假设：传输成功率主要受到 Source 缓存驻留位置和 P2P 接口能力的限制，而不是单纯由前缀深度、复制时机或 Source 身份决定。

#### 2. 建立收益与损失模型

在传输可行性模型的基础上，预测某次主动复制可能带来的收益和成本。

输入主要包括：

- 请求信息及前缀复用情况。（请求信息）
- 缓存状态、Pod 负载与系统容量。（缓存系统状态）
- 主动干预策略及传输参数。（策略与参数）
- 第一步得到的传输可行性估计。

输出包括预期 Saved Prefill、传输开销、无效复制成本、缓存淘汰损失和最终净收益。

用三个数据源标定：

- `per_request.jsonl` → 命中带来的 TTFT 收益（`cache_hit_ratio` 对 `ttfb` 的关系）；

  数据给定了prompt长度，命中cache数，最终TTFB等数据，用来建立请求长度、命中数与TTFT的关系

- `decisions.jsonl` → 决策器估计的 `benefit`/`cost`（对照真实，看高估多少）；

  主要用于进行对照

- `transfer.jsonl` → 真实传输成本（`elapsed_ms`/`bandwidth`）与成功率。

  建立传输成本模型

#### 3. 评估假设性的系统改进

最后，利用模型及模拟器进行反事实分析，比较三种场景：

| 场景                       | 评估重点                                                     |
| -------------------------- | ------------------------------------------------------------ |
| 当前系统                   | 现有 Host/Device 驻留与传输限制下的实际收益                  |
| 支持 Host 传输 Mamba State | 如果历史缓存可以直接从 Host 复制，收益能够提高多少？         |
| Device Pinning             | 如果将热点前缀保留在 GPU，能提高多少传输成功率？额外显存占用是否值得？ |

这一阶段需要量化改进后的收益，也要考虑引入的新成本，例如 Host 传输开销、Device 容量占用和其他缓存被淘汰造成的损失。需要模拟器配合，因为真实日志只记录了现有系统已经发生的操作，无法直接告诉我们“如果支持 Host Mamba 传输，结果会怎样”。

### 目标二：完善多 Pod KV Cache 模拟器，复现真实实验现象

现有的 `ft_local/kvsim_multipod.py` 是一个多 Pod 前缀缓存回放模拟器，支持 AFF、LEAST、REQ 等路由策略，以及 Broadcast、Oracle 等主动干预策略。

但目前模拟器采用**单层 KV Cache 模型**，只记录某个 Pod 是否持有对应前缀，没有区分 Device 和 Host 的缓存驻留状态。执行主动复制时，只要满足目标容量和策略预算，就直接将前缀插入 Target，默认复制能够成功。

这一假设与真实系统不一致，可能导致模拟器高估主动干预的收益。因此，需要在现有模拟器中加入存储分层和传输可行性约束。

具体需要完成三个部分：

1. **增加 Device/Host 分层缓存**：将原有单层 `PodCache` 扩展为 Device Cache 和 Host Cache，分别管理两层的缓存容量、前缀命中与淘汰，并模拟 `write_through` 下的 Host 备份和 Device 缓存回收，使历史缓存的驻留情况能够接近真实实验。
2. **增加 P2P Transfer 可行性检查**：主动复制前，先检查 Source 是否持有完整的待传输前缀，以及该前缀是否位于当前支持传输的存储层。对于混合 Mamba 模型，`DEVICE` 模式要求完整 Device Full-KV，而 `HICACHE_DIRECT` 暂不支持 Mamba State。如果不满足条件，则记录传输失败，不再直接向 Target 插入缓存。
3. **重新运行策略对照实验**：在相同请求 Trace 和参数下，比较原始单层模拟器与分层模拟器的结果，重点观察传输成功率、缓存命中率、Saved Prefill Tokens、网络传输量和负载倾斜程度。

改造后的模拟器需要能够解释并复现真实集群观察到的主要现象：

- 主动复制的传输成功率极低，Broadcast 为 0%，Proactive 约为 1.57%。
- 主动干预没有带来明显的额外缓存命中收益。
- 原始单层模拟器由于默认 KV 可以传输，可能高估主动复制的实际收益。

同时，应尽量保留原有 AFF、LEAST、REQ 基线的统计口径，使改造前后的结果具有可比性。

**总结：** 在现有多 Pod 模拟器中增加 Device/Host 分层缓存及 P2P 传输限制，通过模拟实验解释真实系统中主动干预收益接近零的原因，并为后续评估 Host 直传、Device Pinning 等改进方案提供实验环境。
